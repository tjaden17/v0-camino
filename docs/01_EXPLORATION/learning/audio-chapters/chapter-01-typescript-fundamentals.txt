The TypeScript Mental Model

TypeScript is JavaScript with types. Every valid JavaScript is valid TypeScript, but TypeScript adds a layer on top that describes what kind of data your code expects. Think of types as contracts, promises your code makes about what it will accept and return.

When you write a function in JavaScript, you might write: function add numbers, parameters a and b, return a plus b. This function will happily add two numbers, two strings, a number and a string, or anything else. Sometimes this flexibility is useful. Often, it causes bugs.

In TypeScript, you write: function add numbers, parameters a colon number comma b colon number, colon number, open brace, return a plus b, close brace. Now TypeScript knows this function only accepts numbers and only returns numbers. If you try to pass a string, TypeScript catches it before the code even runs.

This is the magic of TypeScript. Bugs that would crash your app in production get caught while you're writing code.

Type Annotations Versus Type Inference

TypeScript has two ways to know what type something is: you tell it explicitly, or it figures it out automatically.

Type annotations are explicit. You write: const count colon number equals 5. You've told TypeScript that count is a number.

Type inference is automatic. You write: const count equals 5. TypeScript sees the 5 and infers that count must be a number. No annotation needed.

Both are valid. Use annotations when you want to be explicit, especially in function parameters and return types. Use inference for simple cases where the type is obvious.

This tells TypeScript: this function takes an array of Parsed CSV Row objects and returns a Promise that resolves to an array of Signal Requirement objects.

TypeScript can now check every call to discover signals and ensure you're passing the right data and handling the returned Promise correctly.

Interfaces Versus Types

In TypeScript, you can define custom types in two ways: interfaces and types. They're similar but have subtle differences.

An interface describes the shape of an object. In Camino, you have: interface Signal Interpretation with fields signal underscore id colon string, what underscore we underscore found colon string, what underscore it underscore means colon string, and so on. This interface says: any Signal Interpretation object must have these exact fields with these exact types.

A type can do the same thing but is more flexible. You can write: type Status equals quote active quote pipe quote archived quote pipe quote deleted quote. This creates a union type where Status can only be one of those three strings.

The practical difference: interfaces are better for objects that might be extended later. Types are better for unions, intersections, and complex combinations.

In your codebase, you use both. Interfaces for database models like Signal Interpretation, Profile Complete, Org Data Layer. Types for things like Trend Direction which is quote up quote pipe quote down quote pipe quote stable quote.

When should you use which? Here's the rule: if you're describing an object shape that represents real data from your database or API, use an interface. If you're creating a union of possible values or combining types, use a type.

Generics: Types with Parameters

Generics let you write types that accept other types as parameters. This sounds abstract, but you use them constantly in Camino.

The most common example is Promise. When you see: Promise open angle bracket boolean close angle bracket, that's a generic type. Promise is the generic, and boolean is the type parameter. This reads as: a Promise that will eventually resolve to a boolean value.

In your check connection function in the integration architecture module, the return type is: Promise open angle bracket boolean close angle bracket. This tells TypeScript: this function returns a Promise, and when that Promise resolves, the value will be a boolean.

Arrays are also generic. When you write: string open square bracket close square bracket, you're really writing: Array open angle bracket string close angle bracket. An array that contains strings.

Your signal discovery service returns: Signal Requirement open square bracket close square bracket. This is: an array of Signal Requirement objects.

Generics let you reuse logic across different types. The Promise logic works the same whether it's Promise open angle bracket boolean close angle bracket or Promise open angle bracket Signal Interpretation close angle bracket. You don't need separate Promise implementations for each type.

Union Types: This or That

A union type means a value can be one of several types. You create unions with the pipe character.

In Camino, your Trend Direction type is: type Trend Direction equals quote up quote pipe quote down quote pipe quote stable quote. A Trend Direction can only be one of those three strings. If you try to assign quote sideways quote, TypeScript will error.

This is incredibly useful for things like status fields. Instead of accepting any string and hoping it's valid, you explicitly define the valid values. This prevents typos and makes autocomplete work perfectly.

Another example from your codebase: error handling. When you catch an error, it might be an Error object, or it might be a string, or it might be something else. You can type this as: unknown, then narrow it down: if error instanceof Error, then error dot message.

Optional Properties: The Question Mark

In your interfaces, you'll see the question mark symbol. This makes a property optional.

In the Signal Interpretation interface, if a field is marked: context question mark colon string, it means: this field might be a string, or it might be undefined. It's not required.

Without the question mark, the field is required. TypeScript will error if you try to create a Signal Interpretation object without providing that field.

Use optional properties when data might not always be available. For example, a signal might have interpretation data after it's been analyzed, but not immediately after creation. Mark interpretation question mark colon Signal Interpretation.

Type Narrowing: Making Types More Specific

Type narrowing is how you tell TypeScript: I know this value is more specific than its current type suggests.

The most common example is error handling. In a catch block, the error is typed as unknown. You need to narrow it to Error to access error dot message.

You write: if error instanceof Error, open brace, console dot log error dot message, close brace. Inside that if block, TypeScript knows error is an Error object, so it lets you access the message property.

Another example: optional properties. If you have: signal dot interpretation question mark dot what underscore it underscore means, the question mark operator narrows the type. It reads as: if signal dot interpretation exists, access what underscore it underscore means. Otherwise, return undefined.

This prevents the classic "Cannot read property of undefined" runtime error. TypeScript forces you to handle the case where interpretation might not exist.

Debugging TypeScript Errors

TypeScript errors can be intimidating at first. Here's how to read them.

Error: Type string is not assignable to type number.
Translation: You're trying to put a string where TypeScript expects a number. Find where you're assigning or passing the value and check the types.

Error: Property interpretation does not exist on type Signal Data.
Translation: You're trying to access signal dot interpretation, but the Signal Data interface doesn't have that field. Either add it to the interface, or it's a typo.

Error: Argument of type string is not assignable to parameter of type Trend Direction.
Translation: You're passing a string to a function that expects specifically quote up quote comma quote down quote comma or quote stable quote. The string you're passing doesn't match those exact values.

The key: read the error carefully. TypeScript is trying to help you. It's telling you exactly what's wrong and often suggests a fix.

TypeScript Configuration: tsconfig dot json

Your project has a tsconfig dot json file that configures how TypeScript behaves. You rarely need to edit it, but understanding a few key options helps.

strict colon true. This enables all strict type checking options. Without this, TypeScript is very permissive and misses bugs. With it, TypeScript is strict but catches more issues.

target colon quote ES 2020 quote. This tells TypeScript what version of JavaScript to compile down to. ES 2020 includes modern features like optional chaining.

module colon quote ESNext quote. This tells TypeScript to use modern ES module syntax: import and export.

jsx colon quote preserve quote. This tells TypeScript to leave JSX syntax alone. Next dot js handles JSX compilation.

You don't need to memorize these. Just know: the config makes TypeScript stricter and smarter.
