The Database Mental Model: Tables, Rows, and Columns

A database is a collection of tables. Each table stores a specific type of data. Think of a table like a spreadsheet: rows are records, columns are fields.

Your signals table has rows for each signal. Each row has columns: id, name, description, user underscore id, created underscore at, and so on.

When you query the database, you're asking for specific rows and columns. quote Give me all signals where user underscore id equals this value quote or quote Give me the signal with id equals 123 quote.

The power of a relational database is tables can relate to each other. Your signals table relates to your data underscore points table. Each data point belongs to a signal. The relationship is defined by the signal underscore id column in data underscore points, which references the id column in signals.

This is why it's called a relational database. Tables relate to each other through foreign keys.

JOINS: Combining Tables

Joins let you combine data from multiple tables. This is where SQL becomes powerful.

Your signals table and data underscore points table are related. Each data point has a signal underscore id column that references a signal's id. To get a signal and its data points in one query, you use a join.

Example: SELECT signals dot name comma data underscore points dot value FROM signals JOIN data underscore points ON data underscore points dot signal underscore id equals signals dot id WHERE signals dot user underscore id equals quote user 123 quote.

This reads as: Get the name from signals and value from data underscore points, matching rows where signal underscore id equals id, for signals belonging to user 123.

The result includes rows with data from both tables.

There are different types of joins:

INNER JOIN: Only rows where the relationship exists. If a signal has no data points, it's not included.

LEFT JOIN: All rows from the left table, even if there's no match in the right table. If a signal has no data points, the signal appears but data point columns are NULL.

RIGHT JOIN: Like LEFT JOIN but reversed.

Indexes: Making Queries Fast

Indexes make queries faster by creating a fast lookup structure. Without an index, the database scans every row. With an index, it jumps directly to the relevant rows.

Foreign Keys: Enforcing Relationships

A foreign key is a constraint that enforces relationships between tables. In data underscore points, the signal underscore id column has a foreign key constraint:

FOREIGN KEY open parenthesis signal underscore id close parenthesis REFERENCES signals open parenthesis id close parenthesis ON DELETE CASCADE.

This means: signal underscore id must be an id that exists in the signals table. You can't insert a data point with a signal underscore id that doesn't exist. The database will reject it.

ON DELETE CASCADE means: if you delete a signal, all its data points are automatically deleted. This keeps the database consistent.

Foreign keys prevent orphaned data. Without them, you could delete a signal but leave its data points, which would reference a nonexistent signal.

NULL: The Absence of Value

NULL is a special value that means quote no value quote. It's not zero, not an empty string, not false. It's the absence of a value.

A column can be nullable or not nullable. If nullable, it can have NULL. If not nullable, it must have a value.

Example: created underscore at timestamp NOT NULL. This column must have a value. You can't insert a row without providing created underscore at.

Example: deleted underscore at timestamp. No NOT NULL, so it's nullable. It's NULL for active rows, set to a timestamp for deleted rows.

When querying, NULL requires special syntax. WHERE column equals NULL doesn't work. You write WHERE column IS NULL or WHERE column IS NOT NULL.

In Supabase: dot is open parenthesis quote deleted underscore at quote comma null close parenthesis.

Use NULL for optional values. Use NOT NULL for required values. Be explicit in your schema design.

Writing Migrations

Migrations are SQL scripts that change your database schema. When you add a new table or column, you write a migration.

Your scripts slash 00 underscore SETUP underscore DATABASE dot sql file is a migration. It creates all your tables from scratch.

A migration to add a column might look like:

This adds a priority column to the signals table. Existing rows get the default value quote medium quote.

Migrations should be idempotent when possible, meaning you can run them multiple times without error. You do this with IF NOT EXISTS checks:

If the table exists, this does nothing. If it doesn't, it creates it.

Always test migrations on a development database before running them in production. A bad migration can corrupt data or bring down your app.
