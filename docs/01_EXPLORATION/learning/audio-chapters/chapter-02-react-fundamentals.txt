The React Mental Model: UI as a Function of State

React has a simple core idea: your UI is a function of your state. When state changes, React re-renders the component to reflect the new state.

Think of a component as a function that takes data and returns UI. Every time the data changes, React calls the function again and updates what's on screen.

Here's a simple example. You have a counter component. The state is: count equals zero. The UI shows: count. When you click a button and set count to 1, React re-renders the component. The function runs again, this time with count equals 1, and the UI updates to show 1.

This is different from traditional UI frameworks where you manually update the DOM. In React, you never touch the DOM directly. You update state, and React figures out what needs to change.

When to Use State Versus Props

Use state when:
- The data changes over time based on user interaction.
- The data is local to this component.
- The data controls what the component displays.

Use props when:
- The data is passed from a parent.
- The data doesn't change within this component.
- The data is shared across multiple components.

A common pattern: a parent has state, children have props. The parent manages the state, children display it.

Common React Patterns in Camino

Here are patterns you'll see throughout your components:

Pattern 1: Controlled components.
Your form inputs are controlled, meaning their value comes from state. You have: value equals open brace input value close brace on change equals open brace handle change close brace. When the user types, on change updates state, which updates value, which updates what's displayed.

Pattern 2: Lifting state up.
When two components need to share state, you move the state to their common parent. If the signals page and a filter component both need the filter state, the state lives in the page and both children receive it as props.

Pattern 3: Component composition.
Your signal card is composed of smaller pieces: the card wrapper, the header, the content sections. Each piece is a separate component or a well-defined JSX block. This makes the code easier to read and maintain.

Pattern 4: Early returns.
If a component can't render yet, maybe data is loading, return early with a loading state. Don't try to render incomplete data.

Debugging React Issues

When something doesn't update, ask these questions:

Is the data in state? If it's just a variable, changing it won't trigger a re-render. It must be state created with use state.

Are you mutating state directly? Don't do: state dot value equals new value. Do: set state open parenthesis open brace dot dot dot state comma value colon new value close brace close parenthesis. State must be immutable.

Is the key prop stable? If you're using array index as key and reordering the array, React gets confused. Use a stable identifier.

Is the component re-rendering but the UI not updating? Check if you're comparing objects by reference. React's re-render optimization might think nothing changed if you mutate an object instead of creating a new one.

React DevTools: Your Best Friend

Install the React DevTools browser extension. It adds a Components tab to your browser's developer tools. You can inspect the component tree, see props and state for each component, and even edit values to test different scenarios.

When debugging, open DevTools, find the component that's not working, and check its props and state. Often the issue is: the data isn't what you think it is.
