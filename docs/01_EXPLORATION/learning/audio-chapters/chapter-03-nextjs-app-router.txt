Server Components Versus Client Components

This is the most important concept in Next dot js 16. By default, all components are server components. They run on the server, not in the browser.

Server components can directly query the database, access environment variables, and perform expensive operations. They render to HTML on the server and send that HTML to the browser. The browser receives fully rendered content.

Client components run in the browser. They handle interactivity, use hooks like use state and use effect, and respond to user events. You mark a component as a client component with quote use client quote at the top of the file.

This is the Next dot js model: server components fetch data and do heavy lifting, client components handle interactivity.

When to Use Server Versus Client

Use server components when:
- You need to fetch data from a database or API.
- You need to access environment variables that should stay secret.
- You don't need interactivity like buttons or forms.
- You want to reduce JavaScript sent to the browser.

Use client components when:
- You need state with use state or effects with use effect.
- You need event handlers like on click.
- You use browser only APIs like local storage or window.
- You want interactivity.

The common pattern: server component fetches data, passes it to client component, client component makes it interactive.

Middleware: Code that Runs Before Every Request

Middleware is code that runs before a request is processed. It's defined in a file at the root called middleware dot ts.

Your app uses middleware for authentication. Before any protected route loads, the middleware checks if the user is authenticated. If not, it redirects to login.

Middleware can modify requests, rewrite URLs, set headers, or return early responses. It's powerful for cross-cutting concerns like auth, logging, or redirects.

Parallel Routes and Intercepting Routes

Advanced features you might not need yet but should know exist.

Parallel routes let you render multiple pages in the same layout simultaneously. Like a dashboard with multiple widgets, each widget is a separate route but they all render together.

Intercepting routes let you show a route in a modal while the URL changes. Like clicking a signal to open a detail modal, the URL changes to slash signal slash 123 but the modal opens over the current page instead of navigating away.

These are powerful for complex UIs but you probably won't need them in early Camino development.
