THE TYPESCRIPT MENTAL MODEL

TypeScript is JavaScript with types. Every valid JavaScript is valid TypeScript, but TypeScript adds a layer on top that describes what kind of data your code expects. Think of types as contracts, promises your code makes about what it will accept and return.

When you write a function in JavaScript, you might write: function addNumbers, parameters a and b, return a plus b. This function will happily add two numbers, two strings, a number and a string, or anything else. Sometimes this flexibility is useful. Often, it causes bugs.

In TypeScript, you write: function addNumbers, parameters a colon number, b colon number, colon number, return a plus b. Now TypeScript knows this function only accepts numbers and only returns numbers. If you try to pass a string, TypeScript catches it before the code even runs.

This is the magic of TypeScript. Bugs that would crash your app in production get caught while you're writing code.

THE RELATIONAL DATABASE MENTAL MODEL

A relational database organizes data into tables. Think of a table like a spreadsheet: rows are records, columns are fields.

Your signals table has rows, each row is one signal. Columns are signal id, user id, name, category, value, trend, and so on.

The "relational" part means tables can relate to each other. A signal has many data points. The data points table has a signal id column that references the signal. This creates a relationship: one signal to many data points.

This model is powerful because you can query across relationships. "Give me all signals and their data points" becomes a simple join query.

SQL, Structured Query Language, is how you talk to the database. You write queries to select, insert, update, and delete data.

TABLES, ROWS, AND COLUMNS

Let's start with structure. A table is defined by its schema: the columns and their types.

- user underscore id: who owns this signal, text
- name: signal name, text
- category: revenue, sales, marketing, text
- value: the calculated number, float

Each row is one signal. Each column holds one piece of information about that signal.

JWT TOKENS: HOW IDENTITY WORKS

When a user signs in, Supabase generates a JWT, JSON Web Token. This token is a cryptographically signed string that proves the user's identity.

The token contains claims: user ID, email, role, expiration time. It's signed with a secret key only Supabase knows. This means the token can't be forged. If someone tries to fake a token, the signature won't match and Supabase rejects it.

The JWT is sent with every request in the Authorization header. Supabase validates it, extracts the user ID, and makes it available to your code via auth dot uid open parenthesis close parenthesis.

This is how Row Level Security knows who the user is. When you write a policy using auth dot uid open parenthesis close parenthesis, it's reading from the JWT.

TOKEN REFRESH AND EXPIRATION

JWT tokens expire after a set time, usually 1 hour. This limits the damage if a token is stolen.

Before the token expires, Supabase automatically refreshes it. The client library handles this transparently. Your code doesn't need to do anything.

If a refresh fails, the user is logged out and must sign in again.

ROW LEVEL SECURITY: DATABASE LEVEL ACCESS CONTROL

Row Level Security, RLS, is a PostgreSQL feature that filters rows based on policies. Even if your application code has a bug, the database won't return unauthorized data.

Without RLS: Any code that can connect to the database can read and modify any row. If your app has a bug that exposes data, users could see each other's information.

With RLS: The database checks policies on every query. If the policy says "user can only see their own data," the database enforces it. Even if your app tries to fetch all signals, the database only returns signals where user underscore id equals the authenticated user's ID.

RLS is your primary defense against data leaks in multi-tenant apps.

ENABLING RLS

To enable RLS on a table: ALTER TABLE signals ENABLE ROW LEVEL SECURITY.

Now the table is locked down. No one can read or write unless a policy allows it.

Without any policies, even the table owner can't query it. Policies grant access.

In Camino, every table with user data has RLS enabled. Check your migration scripts, you'll see ENABLE ROW LEVEL SECURITY for signals, profiles, uploads, and others.

RLS POLICIES: GRANT ACCESS

A policy defines who can do what. Policies use the USING clause for SELECT and the WITH CHECK clause for INSERT, UPDATE, DELETE.

Example: CREATE POLICY "Users can read own signals" ON signals FOR SELECT USING open parenthesis auth dot uid open parenthesis close parenthesis equals user underscore id close parenthesis.

This policy says: for SELECT queries, include only rows where the authenticated user's ID matches the user underscore id column.

When a user runs: SELECT asterisk FROM signals, the database automatically adds: WHERE auth dot uid open parenthesis close parenthesis equals user underscore id. The user only sees their signals.

For INSERT, use WITH CHECK: CREATE POLICY "Users can insert own signals" ON signals FOR INSERT WITH CHECK open parenthesis auth dot uid open parenthesis close parenthesis equals user underscore id close parenthesis.

This ensures users can only insert signals where user underscore id equals their own ID. If they try to insert a signal for another user, the database rejects it.

USING VERSUS WITH CHECK

USING controls which rows are visible on SELECT.
WITH CHECK controls which rows can be inserted or updated.

For SELECT: USING open parenthesis condition close parenthesis means: only show rows where condition is true.

For INSERT: WITH CHECK open parenthesis condition close parenthesis means: only allow inserts where condition is true after the insert.

For UPDATE: You can use both. USING determines which rows can be updated. WITH CHECK determines what the new values can be.

DELETE uses only USING: which rows can be deleted.

This says: you can update signals where you're the owner, and the update can't change user underscore id to someone else.

SERVICE ROLE VERSUS ANON KEY

Supabase gives you two API keys: the anon key and the service role key.

The anon key is for client-side code. It has limited permissions. RLS policies apply. Even if someone steals the anon key from your frontend code, they can only access data the policies allow.

The service role key bypasses RLS. It has full database access. This is for server-side admin operations where you need to override policies.

Rule: Use anon key in the browser. Use service role key only on the server, in API routes or server components, and never expose it to the client.

TEMPERATURE: CONTROLLING CREATIVITY

Temperature controls randomness. Low temperature means predictable, deterministic output. High temperature means creative, varied output.

Temperature ranges from 0 to 2. Typical values:
- 0: Completely deterministic. Same input always produces same output.
- 0.3 to 0.7: Balanced. Some variation but mostly consistent.
- 1 and above: Creative and unpredictable.

For signal analysis, you want low to medium temperature. 0.3 to 0.5. This keeps the analysis consistent and focused, not random or off-topic.

In the AI SDK: temperature colon 0.5

TOKEN LIMITS: UNDERSTANDING CONTEXT WINDOWS

Language models have a maximum context window, the number of tokens they can process at once. Tokens are roughly words, but not exactly. A token might be a word, part of a word, or punctuation.

GPT-4 has a 128K token context window in some versions. GPT-3.5 has 16K. This includes both the prompt, what you send, and the response, what it generates.

If your prompt is too long, the API rejects it or truncates it.

To check token count, you can use a tokenizer library or estimate: roughly 1.3 tokens per word.

For Camino, your signal interpretation prompts are short. You're sending the signal name, value, trend, and maybe a few data points. Probably under 1000 tokens. Well within limits.

If you add more context, like full CSV data, watch the token count. You might need to sample or summarize data before sending it to the AI.

PROMPT ENGINEERING: CRAFTING EFFECTIVE PROMPTS

The better prompt gives context, role, task, format, and expectations.

Key principles:
1. Be specific. "Analyze" is vague. "Provide 5 sections with specific insights" is clear.

3. Specify format. "Return JSON with these fields" or "Write 3 bullet points" or "Use this structure."
4. Set expectations. "Be actionable, not generic" or "Focus on risks, not opportunities."

This is the pattern: use shadcn primitives for structure, Tailwind utilities for styling, design tokens for colors.

COMMON TAILWIND PATTERNS IN CAMINO

Pattern one: Flexbox for layout. flex items-center justify-between is everywhere.

Pattern two: Design tokens for colors. bg-background, text-foreground, border-border. This ensures consistency.

Pattern three: Responsive utilities with breakpoints. grid-cols-1 md colon grid-cols-2 lg colon grid-cols-3.

Pattern four: Hover states with transitions. hover colon bg-accent transition-colors.
